Prerequisites

Before you start

Goal: Understand what Git and GitHub are, and set up your practice environment.

Git vs GitHub — quick mental model

  • Git is version control software on your computer. It tracks changes to files over time so you can undo mistakes, compare versions, and work on features safely.
  • GitHub is a website that hosts Git repositories online. It adds collaboration tools: issues, pull requests, reviews, and free static website hosting (GitHub Pages).

Think of Git as the engine in your laptop, and GitHub as the garage + team workspace on the internet.

What you need

  • A laptop or desktop with internet
  • A personal email you check regularly (for account verification)
  • Optional but recommended: install Git for your OS and a code editor such as VS Code

How to use this guide

  1. Read one stage fully before jumping ahead.
  2. Do every hands-on step yourself — reading alone is not enough.
  3. Tick off the checklist at the end of each stage.
  4. Watch the linked videos when your mentor adds them (or search YouTube for the stage title).

Stage 1

GitHub account & profile

Goal: Create a professional GitHub identity recruiters and teammates can recognize.

Steps

  1. Sign up at github.com/signup.
    • Use a username you are comfortable showing on your resume (short, readable, no random numbers if possible).
    • Choose the free plan.
    • Verify your email when GitHub sends the confirmation message.
  2. Secure the account
    • Settings → Password and authentication → enable two-factor authentication (2FA).
    • Save backup codes in a safe place.
  3. Complete your profile (click your avatar → Your profile → Edit profile)
    • Add a clear profile photo.
    • Write a one-line bio (e.g. “CSE student | learning GitHub & web dev”).
    • Add your college or city if you are comfortable.
    • Optional: link LinkedIn or portfolio site later.
  4. Explore the dashboard
    • Notice the + menu (new repository, import, gist).
    • Open Notifications and Settings once so you know where they live.
Tip: Your username becomes part of your free website URL: https://<username>.github.io. Pick something you will not regret on a resume.

Stage 1 checklist

  • GitHub account created and email verified
  • 2FA enabled
  • Profile photo and bio added
  • I can find Settings, Notifications, and the + menu

Stage 2

Your first repository

Goal: Create a repository, understand its main screens, and make your first commit on the web.

What is a repository?

A repository (repo) is a project folder tracked by Git. It holds your code, docs, images, and a full history of every change.

Steps — create a practice repo

  1. Click + → New repository.
  2. Set:
    • Repository name: hello-github (or any practice name)
    • Description: optional one line
    • Public (good for portfolio; private is fine for experiments)
    • Check Add a README file — GitHub creates the repo with a first file
    • Choose Add .gitignore → template Node or VisualStudio if you use those tools later (optional for now)
    • Click Create repository
  3. On the repo home page, identify:
    • Code tab — files and folders
    • Issues — bugs and tasks
    • Pull requests — proposed changes
    • Settings — permissions, Pages, branch rules
  4. First commit via the website
    • Open README.md → pencil icon (Edit).
    • Add a line: Hello GitHub — my first repo.
    • Scroll down, write commit message: Update README with intro line
    • Choose Commit directly to the main branch → Commit changes.

Read the commit history

Click the commit count link (e.g. “2 commits”) near the top. Each commit shows who changed what and when. This history is the core value of Git.

Stage 2 checklist

  • I created a repository with a README
  • I edited a file and committed on the web
  • I can open the commit history and see my change
  • I know where Issues and Pull requests tabs are

Stage 3

GitHub Pages — your username.github.io site

Goal: Publish a simple personal webpage hosted free on GitHub.

Two common patterns

PatternRepo nameLive URL
User site (personal homepage) <username>.github.io https://<username>.github.io
Project site (one project) any name, e.g. hello-github https://<username>.github.io/hello-github/

Start with a user site — it is the classic “my first website on GitHub” milestone.

Steps — user site

  1. Create a new public repository named exactly <your-username>.github.io (replace with your real username).
  2. Add an index.html file:
    • Click Add file → Create new file
    • Filename: index.html
    • Paste minimal HTML:
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>My GitHub Page</title>
</head>
<body>
  <h1>Hello, world!</h1>
  <p>This is my first GitHub Pages site.</p>
</body>
</html>
  1. Commit the file to main.
  2. Go to Settings → Pages (left sidebar).
  3. Under Build and deployment, Source = Deploy from a branch, Branch = main / / (root) → Save.
  4. Wait 1–3 minutes. GitHub shows your live URL at the top of the Pages settings.
  5. Open the URL in a browser. You should see your heading.
Tip: If the page 404s, wait a bit longer, confirm the repo is public, and check that the file is named index.html on the main branch.

Stage 3 checklist

  • I created username.github.io (or a project Pages repo)
  • index.html is committed on main
  • Pages is enabled in Settings
  • My site loads in the browser

Stage 4

Add & edit code

Goal: Put project files on GitHub using the web UI and, optionally, your own computer.

Method A — Upload on GitHub.com (no install)

  1. Open your repo → Add file → Upload files.
  2. Drag folders or files from your computer.
  3. Write a clear commit message (e.g. Add project HTML and CSS).
  4. Commit to main.

Good for small updates. For daily coding, Method B is better.

Method B — Clone, edit locally, push (recommended)

  1. Install Git if you have not already. In a terminal, confirm: 
    git --version
  2. On GitHub, open your repo → green Code button → copy the HTTPS URL.
  3. Clone to your machine: 
    git clone https://github.com/<username>/<repo>.git
cd <repo>
  4. Edit files in VS Code or any editor. Save changes.
  5. Send changes back to GitHub: 
    git status
git add .
git commit -m "Describe what you changed"
git push origin main
  6. Refresh the repo on GitHub — your files and new commit appear online.

Good file habits

  • Keep a useful README.md (what the project is, how to run it).
  • Do not upload passwords, API keys, or .env files — use .gitignore.
  • Commit often with messages that explain why, not only what.

Stage 4 checklist

  • I uploaded or cloned files successfully
  • I made an edit and see it on GitHub
  • My README describes the project
  • I know not to commit secrets

Stage 5

Essential Git commands

Goal: Learn the small set of commands you will use every day.

Run these inside your project folder (after git clone or git init). Git commands are the same on Windows, Mac, and Linux.

git init

Start a new Git repo in the current folder. Use once per new local project (GitHub’s “create repo” flow often skips this because git clone already sets it up).

git init my-app
cd my-app

git clone

Download a copy of a remote repository (usually from GitHub).

git clone https://github.com/<user>/<repo>.git

git status

Shows modified, staged, and untracked files. Run this constantly — it tells you what to do next.

git status

git add

Stage changes for the next commit. . means all changes in the folder.

git add index.html
git add .

git commit

Save a snapshot locally with a message. Commits should be small and logical.

git commit -m "Add contact section to homepage"

git push

Upload local commits to GitHub (remote).

git push origin main

git pull

Download and merge the latest changes from GitHub. Use before starting work if others (or you on another PC) pushed updates.

git pull origin main

git log

View commit history. --oneline gives a compact list.

git log --oneline

The daily loop

git pull          # get latest (if working with others)
# ... edit files ...
git status        # see what changed
git add .
git commit -m "Clear message"
git push          # share on GitHub

Stage 5 checklist

  • I ran git status and understand its output
  • I made a commit with a meaningful message
  • I pushed to GitHub and saw the commit online
  • I can explain add → commit → push in my own words

Stage 6

Branches & merging

Goal: Work on features safely without breaking the stable main branch.

Why branches?

main (or master in older repos) should stay in a working state. Branches let you experiment, build a feature, or fix a bug in isolation, then merge when ready.

Branch workflow — practice exercise

  1. Create and switch to a new branch: 
    git checkout -b add-about-page

    Modern alternative: git switch -c add-about-page

  2. Create or edit files (e.g. add about.html or update README).
  3. Commit on the branch: 
    git add .
git commit -m "Add about page"
  4. Push the branch to GitHub: 
    git push -u origin add-about-page
  5. On GitHub, open Pull requests → New pull request. Base: main ← Compare: add-about-page.
  6. Review the Files changed tab. If it looks correct, click Merge pull request.
  7. Locally, switch back and update: 
    git checkout main
git pull origin main

Merge conflicts (brief)

If two branches edit the same lines, Git may ask you to resolve a merge conflict. Open the conflicted file, look for <<<<<<< markers, choose the correct content, then:

git add <file>
git commit -m "Resolve merge conflict"

Do not panic — conflicts are normal when collaborating. Ask your mentor if you get stuck on your first one.

Useful branch commands

CommandPurpose
git branchList local branches
git switch <name>Change branch
git merge <branch>Merge another branch into current branch
git branch -d <name>Delete a merged local branch

Stage 6 checklist

  • I created a branch and committed on it
  • I opened a pull request on GitHub
  • I merged the PR into main
  • I updated my local main with git pull

Stage 7

Collaboration

Goal: Contribute to shared projects politely and effectively — the way real teams ship software.

Roles on a shared repo

  • Owner / maintainers — manage settings, review PRs, merge code.
  • Contributors — fork or branch, push changes, open pull requests.
  • Everyone — uses Issues to report bugs and discuss work.

Workflow A — same team, one repo

Typical for college project groups when everyone is added as a collaborator:

  1. Owner adds teammates: Settings → Collaborators.
  2. Each person clones the repo.
  3. Before coding: git pull origin main.
  4. Create a feature branch → commit → push → open PR.
  5. Teammate reviews → merge → others pull latest main.

Workflow B — open source (fork model)

Used when you do not have direct write access (most open-source projects):

  1. Click Fork on the upstream repo (creates a copy under your account).
  2. Clone your fork, create a branch, make changes, push to your fork.
  3. Open a PR from your fork to the original repository.
  4. Maintainers review; you address feedback with more commits on the same branch.

Issues & pull requests — team etiquette

  • Issues: one topic per issue, clear title, steps to reproduce for bugs.
  • PR title: says what the change does (“Fix navbar on mobile”, not “Update”).
  • PR description: what changed, why, how to test.
  • Link PR to issue: “Closes #12” auto-closes the issue when merged.
  • Review classmates’ PRs kindly — ask questions, suggest improvements.

Protecting main (teams)

Many teams enable branch protection: no direct pushes to main, require PR review before merge. Ask your mentor to demonstrate in a demo org repo.

Stage 7 checklist

  • I cloned a shared or forked repo
  • I opened an Issue or commented on one
  • I submitted a PR and described my changes
  • I reviewed someone else’s PR (or a practice PR from mentor)
  • I understand fork vs collaborator access
